# Task Lifecycle

Mandatory final Skill reporting: keep an internal record during work of each exact Skill name actually used, its task step or action, and the reason or purpose for using it. Read and follow a Skill before claiming use; collect the same actual-use details from delegated branches. Do not require repeated Skill inventories at startup, resume, analysis, task decomposition, execution, verification, deployment, cleanup or progress updates. In one final response, including partial, failed or paused outcomes, summarize all actual Skill use across the task and branches with names, steps and reasons. Distinguish planned but unused, missing or unreadable Skills separately; if none applied, say Skills: none and why. Correct omissions before completion. Follow task-analyze-skill/SKILL.md#mandatory-visible-skill-reporting. Report actions and results without private chain-of-thought.

For device testing, prefer an available authorized physical device. If none is available, automatically run the supported tests in a compatible Android emulator or iOS Simulator without asking or waiting for a device. If the local host cannot run the required ABI, use the configured compatible remote host. Label the runtime scope and distinguish real provider callbacks from Fake, test-network, and store evidence; report any remaining provider or runtime limitation after completing the tests that can run.

Read the request, related skills, and relevant existing project memory. Before detailed execution, briefly explain the result, qualitative difficulty, actual known models, parallel branch roles and real dependencies. Say inherited or model ID not exposed when appropriate; never invent model names. Use one sentence for simple work and a short branch plan when needed.

Automatically name each Chat at most once, using a concise module, system, component or file name such as `Pantone Helper`, `WeatherManager` or `BOM System`. A creation-supplied or user-chosen title counts; retain the first confirmed naming record only in that Chat's own history. Later turns, resume and target changes preserve the current title; uncertain history skips automatic renaming. Only an explicit later human rename request overrides the lock without replacing the first record. Follow `task-analyze-skill/SKILL.md#correct-task-names`.

Follow the action completion rule in `task-analyze-skill/SKILL.md`: carry out requested work, recover from failures while useful authorized routes remain, and lead with delivered changes. Separate verification blockers from implementation; report a concrete evidenced reason when the affected work truly cannot proceed.

Git delivery is one complete transaction. A request to commit, merge, restore or push includes authorization to normally push the task-owned commits on the selected branch to its existing configured upstream, unless the user explicitly requests a local-only commit or no push. A local commit is an intermediate state; continue through remote delivery in the same task.

For every Git-managed update, inspect the current branch, configured upstream, index and dirty files; preserve unrelated work; then fetch and merge the latest upstream before scoped changes. Complete the changes and necessary verification, stage only task-owned changes, and commit immediately. Before every push, fetch again and merge the latest configured upstream into the same branch, resolve conflicts without discarding either relevant intent, and rerun affected checks when integration changes the result. Then perform a normal push. If the remote advances and rejects the push, repeat fetch, merge, conflict resolution and affected verification, then retry the normal push while a useful authorized route remains. Use merge for upstream integration and preserve published history. Never guess a missing upstream, force-push or publish unrelated work or additional branches.

Declare Git delivery complete only after a fresh remote-ref readback matches local HEAD and all task-owned file changes are committed. Report the branch, upstream and delivered commit hash. A missing target, unavailable network or credentials, or an unresolved conflict leaves remote delivery pending: report the exact blocker, unpushed commit hashes and minimum recovery action, and distinguish committed locally from pushed remotely. Restore and verify every temporary integration stash in the same task, then drop only that exact consumed stash; preserve unrelated existing stashes and recoverable conflicting snapshots.

Start ready independent work promptly; serialize only real prerequisites, shared mutable owners and required authorization. Prepare downstream work while external jobs run, use bounded checks and keep exact pending recovery state instead of endless waiting. A confirmed submission completes that step without claiming backend completion. Return to unused owned tabs during final cleanup. Follow workflow-skill/SKILL.md for these states. The user can interrupt or adjust direction; ask only for materially missing decisions or required authorization.

For every UI or visual presentation task (websites, tools, PDF reports, documents, or slide presentations), read and apply `workflow-skill/references/readable-ui.md` from the installed Skills root. This baseline applies even without code changes or when another Skill owns rendering/export; carry it into delegated goals.

For any browser-based test, prefer the Codex or ChatGPT built-in browser surface. Use a named external browser only when the user explicitly requests that browser. If the built-in browser is unavailable, record that limitation and do not silently switch browsers or present a fallback as equivalent evidence.

Verify changed code and consequential results in the active task through one real behavior check or output readback at the smallest relevant boundary. A quick check or mock is not acceptance. Do not launch the whole project or a full build unless requested. Report actual evidence and limitations.

For an identifiable project, before creating a maintained Python test file or starting extended testing, inspect and read its applicable project testing Skill. If none applies, create `.agents/skills/testing-skill`. Maintain a stable purpose/goal/level/relative-path/runner map there; prefer new maintained scripts in that Skill's non-runtime tests directory, but leave toolchain- or release-required tests in their native project paths and track them. Consolidate duplicate-purpose cases and retire obsolete scripts without losing distinct coverage. Use verify-skill/SKILL.md#project-testing-skill-and-test-levels: level 1 focused function/syntax, level 2 real affected case by default, level 3 all related code, level 4 full-system/release only when requested or required. Test output, fixtures and tool caches stay in the isolated external task owner from the first write.

Run scripts, tests, and background work without visible windows or focus changes. Follow `code-skill/references/skill-platform-compatibility.md` from the installed Skills root: prefer Python, preserve supported platform differences, hide each Windows subprocess, and use application-native headless modes. Capture output and preserve failures, timeouts, and cancellation. Open or activate a terminal, browser, report, or app only when the user explicitly asks to show it.

Ensure a real Obsidian memory vault through `project-memory-skill/scripts/obsidian_vault_setup.py` before recall or memory writes. If none exists, generate it from `qinbatista/qin-llm-wiki` outside Codex and project folders; report its exact path and tell the user to back up the whole vault regularly because it holds all Codex and project memory. If setup fails, leave writes pending without a local fallback. Missing matching project notes are a normal read skip.

On a replacement computer, restore or sync the existing whole vault first. A registered or configured vault that is unavailable remains pending; never create an empty replacement. The public generator is a first-vault template, not a private-memory backup.

Durable memory belongs only in the configured Obsidian vault, organized under its exact project or explicitly shared owner. Use `project-memory-skill/scripts/project_knowledge.py recall --project-root ROOT --vault VAULT` with relevant module/file/symbol filters; method recall requires a module, exactly one file, and one or more symbols. Missing indexes or owner conflicts skip recall without unscoped fallback. Keep current knowledge centralized in `Projects/<owner>/Memory.json` with its readable `Knowledge.md` view; preserve history in the existing event store. Record architectural and structural changes and meaningful method contracts without creating a file for every module, method, or task. Keep retired and superseded facts historical. Exclude stale entries and methods without source hashes from current context; return the latter separately as unverified pointers. Refresh consequential claims against current source. Cross-project links are reference pointers whose content is read only when explicitly selected, never silently merged into the active project's facts.

Never write memory, pending queues, coverage records, memory path pointers, or time-varying project information under Codex's local folders or project Cache. Project `AGENTS.md` and Skills contain stable operating rules and how the project works, not a changing memory log. Review and update their relevant rules when the rule itself changes.

Apply Project Memory’s native-deletion preflight before creating a saved Ending; if the creating service has no verified deletion route, finish scoped memory/resource closure in the current chat without creating another conversation. After the main result and real in-task verification finish, launch one authorized visible projectless Ending with the app defaults, then show the acknowledged link and immediately end the main turn. The originating thread must never wait for Ending at any stage: no polling, branch-result collection, later resumption or deletion follow-up. Pass its exact originating thread ID, host when available, project, established evidence and resource handoff. Ending owns memory setup, scoped knowledge merging, due synthesis, the parallel Workflow resource audit, all readbacks, recovery and mandatory self-deletion. It resolves missing or inconsistent context by reading the originating thread with read_thread, without messaging, waking or waiting for it. Read workflow-skill/references/ending-resource-audit.md and follow resource owners; preserve active/shared/user-opened resources, unsaved work and user review/reuse. Memory failure never blocks cleanup. Keep Ending unpinned. Inside Ending, record and read back both completed or explicitly skipped branches before deleting only its own conversation through a supported native action. Use project-memory-skill/scripts/ending_conversation.py when no desktop delete tool is exposed. Verify conversation absence and local-record deletion; archival retains records and never completes the deletion obligation. An unavailable native action stays Ending-owned and never returns cleanup to the parent. Follow project-memory-skill/SKILL.md#ending-conversation-cleanup; never purge Codex databases/session files. Ending never tests, builds, repairs code, benchmarks, publishes or creates further tasks. Creation failure is reported once without holding the main result open.

Bounds-check targets and use the portable lifecycle helper; preserve unrelated work and retained resources. When goals change, remove obsolete or duplicate tests and revise useful cases before adding files. Shipping tests belong in a versioned non-runtime test area. Publish or install only when authorized, with recoverable replacement and preservation of user AGENTS files.
