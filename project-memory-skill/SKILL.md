# Project Memory

Before support/probe writes, apply the [project Cache artifact policy](../workflow-skill/references/project-cache-artifact-policy.md). Isolate them in the owning project Cache from the first write; durable memory keeps its configured Obsidian owner.

Memory reduces repeated explanations. Preserve project problems and user struggles/corrections, attempted solutions, last verified state and date, actual results and evidence, unresolved items and next steps, alongside architecture, ownership, contracts, decisions and preferences in one project knowledge store. Capture useful established outcomes at completion, failure or pause; retain the actual blocker, partial or failed result and next step without inventing proof. Use the existing reason, result, decisions, verification and risks fields; do not invent whole-project status from a passing check. Read [project knowledge](references/project-knowledge.md) for scoped recall, addressable entries, and consolidation.

## Recall before work

When the current task prohibits creating external directories, invoke `scripts/obsidian_vault_setup.py --project-root PROJECT_ROOT --existing-only`. This mode reuses an existing vault and returns `pending` with `vault_creation_disabled` if creation would be needed, without creating parent directories, cloning or running the generator. Skip unavailable recall without creating a fallback. An explicit `--vault` path alone does not lift this boundary.

Resolve the actual project first. Run `scripts/obsidian_vault_setup.py --project-root PROJECT_ROOT` to find the configured memory vault. If none exists, it connects to [qin-llm-wiki](https://github.com/qinbatista/qin-llm-wiki), generates a private vault outside Codex and the project, and verifies it. Use `--vault PATH` for a chosen durable location or `--source PATH` for an offline copy of the generator. Never place the vault in `CODEX_HOME` or project `Cache`. Report the exact returned vault location and tell the user to back up the whole vault regularly because it holds all Codex and project memory. If setup fails, report the reason and leave writes pending without local fallback.

On a replacement computer, restore or sync the existing whole vault before memory setup or new writes. A registered or configured vault that is unavailable or still syncing is pending; wait for that vault instead of generating an empty replacement. The public generator provides structure for a first vault, not a backup of private memories. Verify the restored `AI Memory` and `Projects` contents before claiming recovery.

Use `scripts/project_knowledge.py recall --project-root ROOT --vault VAULT` with at least one relevant task module, project-relative file or meaningful query; method lookup also needs the exact symbol filters. An unfiltered call is a skip, while explicit `--include-project-context` without task selectors returns only project facts and navigation. Method recall requires a module, exactly one file, and one or more symbols; filter types combine with AND. Start from current entries and their relevant relationships; expand to project architecture only when ownership or dependencies require it. Historical events explain provenance and are not the default task context. Read shared preferences only from their explicit shared owner.

Current knowledge lives in `Projects/<owner>/Memory.json`, with a readable `Knowledge.md` view. Existing `AI Memory/events.jsonl` preserves history, including prior failed attempts and superseded solutions. Repeated issues use a stable issue ID with one revision per distinct outcome; identical replays add nothing. Issue resolution is explicit and separate from check status. Do not create a memory file for every task, module, or method, or prepopulate entries for untouched code. Legacy Codex-local memory is read-only migration input, never an ongoing memory owner. A missing index, matching project, or entry is a normal read skip after vault setup; an owner conflict also skips recall. Never fall back to an unscoped history search or another project's memory.

For an unknown module label, use `project_knowledge.py scopes --project-root ROOT --vault VAULT --query TASK_TERMS` (or `--file FILE`) to locate bounded identifiers without loading facts. Recall only the selected scope through the normal freshness gate; discovery pointers are not current evidence.

Use the index in this order: project → task-relevant memory → underlying logic. After scoped recall, `project_knowledge.py logic` with the same task selectors follows declared `applies-logic` relationships to a shared `logic.*` principle and related case pointers. Excluded stale/unverified scopes retain reviewed logic pointers, with their claims withheld; retired scopes supply no routes. If no task link exists, identify the principle from the request/current source and select it explicitly with `--principle-owner OWNER --principle logic.KEY`. Matching keywords alone do not establish matching logic. Read only selected exact-owner references, compare the common principle, applicability and concrete differences, and retain dates/proof limits. Cross-project implementations remain reference material, never facts about the active project. See [the logic contract](references/project-knowledge.md#project-task-and-underlying-logic).

Current user intent and source evidence take precedence over memory. Entries are current or explicitly retired; superseded versions remain history. Recall excludes stale entries and returns methods with absent source hashes separately as unverified pointers, never eligible current context. Current status or a matching source hash does not prove runtime behavior. Refresh consequential claims against current source or actual output. Registered aliases may represent one project, while unregistered clones remain separate.

Keep Codex's automatic memory injection and generation disabled when Obsidian is the memory owner; injected summaries can span unrelated projects. Ordinary recall never loads event history or prose as a fallback for a structured owner. Select historical evidence explicitly and keep it separate from current authority. When the user requests legacy cleanup, remove obsolete imports, duplicate owners and retired routing or coverage files after verifying the current handoff; update references and remove unused writers. Do not create replacement archives or compatibility copies. The canonical event store remains the single useful chronology.

Existing conversations can retain an earlier injected memory instruction after configuration changes. Check effective settings separately from their retained context and subsequent reads; an API acknowledgement or compaction does not prove removal. If the owning service has no supported context repair, report that boundary and prepare a minimal exact-project handoff for a clean conversation, preserving the original record. Creating that conversation requires explicit user authorization; a history-copying fork carries the same risk. Never edit Codex session/database files or substitute another service's unloaded-thread state for the owning app's state.

For a verified move or second-machine checkout, use the explicit `project_knowledge.py register-alias` repair described in [project knowledge](references/project-knowledge.md#registered-root-aliases). It requires the exact registered root, expected owner, stored project key, and current index SHA. Ordinary recall never registers an alias or adopts memory by project name.

## Ending: project guidance, memory and resource closure

Before creating a saved Ending, verify a native deletion route on the service that will own it: an exposed delete tool, or `ending_conversation.py probe --origin-thread-id ORIGIN_ID` confirming that service owns the origin. Without that route, complete project-guidance reconciliation and scoped memory/resource closure in the current chat and create no saved Ending. Do not leave future cleanup to an unavailable API. `prepare_launch` defaults to `inline_required`; pass `--native-delete-available` only with this evidence. This fallback prevents records that neither the app nor CLI can remove automatically.

Apply [automatic project AI index maintenance](../management-skill/references/project-ai-index.md) before the main task's commit/publication. Ending performs a residual `project_ai_index.py inspect --project-root ROOT --project-scope current --phase end` only for the originating current task project, even with an empty memory outcome or no supplied plan. Consulted projects remain references: no AI-index prompts or maintenance there. Established user intent and current scoped source authorize necessary maintenance of existing guidance without another request. Missing bootstrap consent remains pending; Ending cannot infer approval for discovery or first creation. Use the same guarded apply/check helper; preserve unrelated edits, hard constraints and read-only boundaries. Do not create more `AGENTS.md` files or change plugin/global Skills, product code or tests. Residual Ending edits remain local-only unless delivery is separately authorized; never infer publication permission.

Pass optional reviewed guidance changes with `ending_memory_launch.py prepare --project-index JSON`, separately from its memory outcome. The helper binds the handoff to the exact project/origin and validates supplied source hashes, document preimages and target scope through the shared index owner. A stale plan requires bounded current-source/guidance reading and the exact originating thread; rebuild it only when established facts support the change, otherwise record pending. Before applying a revised plan, use `refresh-index --packet JSON --project-index JSON` to validate and replace the handoff plan while preserving its project/origin. Refresh cannot clear `read_only` or `no_project` boundaries; explicit originating reauthorization must use normal `prepare`. Never refresh old memory proof to satisfy the index check. Completion requires a separate `--index-result JSON` identifying the project/origin, status, evidence source and changed files. The launcher checks current guidance, every intended postimage/deletion, and unchanged evidence sources; an old valid index does not prove application. Evidence files updated by the plan are checked against their intended postimages. An explicit read-only/no-project handoff accepts only its matching skip without changed files or a pending result. Missing, malformed or stale guidance remains pending while independent cleanup continues.

When the route is available and the main result and real verification finish, launch one authorized projectless Ending with the app's defaults for useful memory and the [Workflow resource audit](../workflow-skill/references/ending-resource-audit.md). The originating thread must never wait for Ending at any stage. Once the app acknowledges creation, show its actual link and end the main turn immediately: no completion wait, polling, branch-result collection, deletion follow-up, or later resumption for Ending. Creation failure is reported once without holding the main result open. Give Ending the exact origin thread ID, host when available, project, established evidence and resource handoff. Ending owns all subsequent work, readbacks, recovery and removal. When context is missing or inconsistent, it reads the exact originating thread through `read_thread`, including older turns as needed, without messaging, waking or waiting for that thread.

Give a new Ending the creation title `Ending Task | <project>`, using the originating project's directory name; this counts as its first name under [Task Analyze](../task-analyze-skill/SKILL.md#correct-task-names). Preserve it thereafter and keep it unpinned; do not move, reorder, open or duplicate it automatically. Within Ending, run guidance/memory work alongside resource cleanup and collect their records there. Follow resource owners' cleanup first and preserve active work and user review/reuse. Unavailable memory or guidance stays pending while cleanup continues. Ending never tests or repairs the product, builds, benchmarks, publishes by inference or creates further visible tasks. Its status never changes the completed main result.

Consolidate touched entries on every memory branch: read their prior current state, incorporate established changes, and save complete current truth with relevant relationships. A method update does not replace its module summary. Retire exact old scopes for a rename or deletion, and preserve unrelated facts. Record the resulting contract and actual verification status without duplicating summaries. Source evidence belongs to the originating task; capture minimal per-entry files and dependencies supporting that claim, using shared hashes only when every entry depends on those files. Ending must not trim old hash bundles or rehash old claims to resolve staleness.

Synthesis is due immediately for nonempty current knowledge without valid synthesis, and after 20 distinct writes or 30 days. Check exact-owner cadence even without new durable facts. Refresh due summaries in the same Ending, using eligible current scopes and their proof limits; synthesis is navigation only, never eligible current evidence. Its contributor IDs and source checks are bounded; stale, retired or unknown contributors leave memory pending rather than becoming current claims. Use consolidation-only closeout without invented files or verification, and guarded index SHA readback for a reviewed draft. Completion requires the writer's maintenance_due=false; an unavailable or bounded input set leaves memory pending while resource cleanup continues. No automation or extra task chain is required. Skip memory when neither durable updates nor useful consolidation is needed; skip Ending only when guidance reconciliation and the resource audit are also unnecessary or already completed inline.

Use the supported memory writers, never hand-edit event or memory index stores. `scripts/ending_memory.py` remains a memory-only writer with event provenance and central knowledge readback; project guidance never enters its payload. `scripts/ending_memory_launch.py` prepares independent guidance, memory and resource work; app acknowledgement releases the parent, while Ending alone records branch and removal results. Optional creation readback must never become a parent wait. Use `--skip-resource-audit` only when explicitly unnecessary. A user request to use this lifecycle authorizes that task. Ending reads back the event and current knowledge before reporting memory success; an unavailable vault remains pending without a local queue.

### Ending conversation cleanup

Deletion of Ending's own conversation is mandatory after its branch records are saved and read back. Keep the exact origin thread protected. Use an exposed native delete tool when available; otherwise use `scripts/ending_conversation.py`, which calls Codex's documented `thread/delete` API through the running local daemon’s WebSocket transport using the native CLI proxy, or a quiet stdio app-server when no daemon is running. A missing desktop delete tool does not establish that native deletion is unavailable. Do not use Computer Use to operate Codex or edit/purge its databases or session files.

On the host that owns this Ending, run the helper with the host's Python interpreter:

```text
python ending_conversation.py delete --thread-id ENDING_ID --expected-title "Ending Task | PROJECT" --origin-thread-id ORIGIN_ID --apply
```

Resolve the script from this Skill's actual installation. The helper defaults to `codex` on PATH; use `--codex EXECUTABLE` only for a discovered native Codex binary. It reads the exact title again, preserves the origin, checks all providers and archive states, calls native deletion, and verifies both list absence and the native rollout path's absence. It never deletes files directly. `thread/delete` also removes spawned descendants: inspect them first, finish/release owned workers and pass each reviewed ID with `--descendant ID`. Unknown or active descendants block that deletion. If a separate stdio server reports an active writer, connect to the owning daemon; never remove its lock or restart it. A separate stdio server's `notLoaded` state does not prove inactivity on another live client; use the owning app's current state before deleting another Ending. Ordinary automatic closeout deletes only itself; a user's explicit bulk cleanup may delete a reviewed list of local Endings with the same guards.

Save useful outcomes and any recovery records before self-removal. A successful delete may terminate the turn: stop immediately afterwards, with no new message, rename, archive, or record write that could recreate the conversation. The native delete receipt plus all-provider active/archived list and rollout-absence readbacks are the completion evidence. Archiving only hides a conversation and must not replace deletion. Never finish normally with a completed Ending still listed merely because the desktop tool lacks a delete method.

If the native API actually rejects deletion or the required CLI is unavailable, report the exact attempted route and error, preserve the outstanding obligation in its established recovery owner, and keep the result pending. Do not manufacture a successful receipt, repeatedly poll an unchanged failure, restart Codex, or create another cleanup task. The parent never waits or resumes for this recovery.

`ending_memory_launch.py complete` makes `conversation_cleanup` ready after branch readbacks pass. Its `cleanup --packet JSON --removal-result JSON` accepts the helper's exact-thread native receipt; only verified local deletion completes the lifecycle. Legacy archived receipts remain deletion pending and never count as success.

Shared facts stay under their explicit vault owner. Automatically maintain the project's root contract and AI index when established intent, structure or ownership changes, following the [authoring rules](../management-skill/SKILL.md#authoring-rules). This narrow standing authorization does not cover unrelated Skills. Task logs, dated results, unverified ideas and memory consolidation alone never become instructions; changing outcomes and history stay in the vault.

## Isolation and privacy

- Require exact project identity for ordinary recall and writes. Cross-project comparisons or deliberately selected reference links are separate reference material, never authoritative facts about the active project. Do not search or merge unrelated projects by similar names.
- Keep project-specific decisions in that project. Only explicitly general preferences belong in shared memory.
- Save concise facts and project-relative files, not raw prompts, transcripts, reasoning, credentials, absolute host paths, or other projects' content.
- Do not hand-edit event stores. Read back the saved result from Obsidian before claiming it is saved.
- Preserve unrelated records and useful history. Put probes in an isolated project Cache task store under the [artifact policy](../workflow-skill/references/project-cache-artifact-policy.md); never test against production memory.
- Never put durable memory, dated project outcomes, pending memory queues, coverage records, or memory location pointers in `CODEX_HOME`, `~/.codex`, project `Cache`, or project `AGENTS.md`/Skill files. Those project files contain stable rules and workflow instructions only.
