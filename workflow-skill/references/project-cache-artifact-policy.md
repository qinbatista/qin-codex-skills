# Project Cache Artifact Policy

Before any task-selected write, classify maintained source, final deliverables, actual runtime resources, durable memory and temporary task support. Put screenshots, logs, receipts, snapshots, temporary scripts, test output and tool caches in the owning project's ignored `Cache/temp-<task>/` from their first write. Projectless work uses the current workspace Cache; missing workspace or ownership blocks the write. Never fall back to system Temp, Desktop, source folders or Codex storage.

Use `workflow-skill/scripts/task_artifact_paths.py` to allocate a fresh `Cache/temp-<task-key>-<run-id>/` for each execution. Reopen an allocated run by its exact ID and bind child `TMP`, `TEMP` and `TMPDIR` to it. Configure output and caches before launch. Reject links and reparse paths; in Git projects verify Cache is ignored and untracked before writing. Maintained source, requested deliverables, canonical runtime and asset owners and Obsidian memory retain their own boundaries.

On macOS, project Cache must also be excluded from Time Machine; Git ignore does not exclude backups. Before registration or payload writes, the allocator checks native `tmutil isexcluded -X` output for the unchanged, link-free Cache identity. An excluded ancestor suffices; only an included directory receives default sticky `addexclusion`, followed by verified readback. Missing tools, native errors or unverified exclusion block allocation. Other platforms make no Time Machine calls. Sticky exclusion follows directory moves/copies but is lost when its root is deleted: recreate Cache through this owner so exclusion is restored before writing. This is no fixed-path or basename wildcard rule, and it does not remove existing backups or snapshots.

## Separate executions and continuation

For an isolated source/build/test snapshot, use the producer's source-file allowlist, including only explicitly required untracked inputs. Never recursively copy a project with its `Cache`, `Library`, `Temp`, `Logs`, previous snapshots or task store into another run; a nested cache can otherwise multiply every earlier build. Check the selected roots, destination containment and file/byte inventory before copying. Canonical reusable runtime caches stay with their actual owner rather than being cloned per attempt. The producer must release its snapshot on success, failure, timeout and cancellation after verified result or minimum recovery handoff.

A new request, resumed execution or newly started test, build, package or deployment unit allocates a new run, even in the same window, chat or logical task. Never append later output to an earlier run or keep one growing directory for the chat's lifetime. An exact active run remains available to its own consumers; this does not protect completed sibling runs.

Before allocating the next run, execute the [task-transition cleanup checkpoint](task-resource-lifecycle.md#task-transition-cleanup-checkpoint). Unrelated work triggers cleanup too: delete confirmed unused predecessor support without copying it into the new run. The allocator registers exact run ownership in the project Cache operational index; keep lifecycle state current and run the finish checkpoint after delivery. Every checkpoint also checks other tasks' registered completed/obsolete disposable runs immediately and foreign working runs after at least 24 hours of inactivity. Fresh allocation alone does not discharge old-run cleanup.

For a scoped executable producer, `task_artifact_paths.task_artifact_scope(project_root, task_id, borrowed_root=...)` closes its own registered run on every exit and preserves a borrowed outer owner. Move any requested evidence to its actual owner before leaving the scope. A failed closure remains visible with its exact pending reason; it cannot silently become successful cleanup.

For continuation, allocate the new run first and inspect the earlier run's purpose, exact identity and current consumers. Copy only genuinely useful inputs, fixtures or minimum resumable state; do not copy its whole scratch tree, logs or build caches merely because they exist. Verify copied bytes and update consuming paths through a fresh reader. Delete the confirmed disposable old run once no live or recovery consumer still needs it, or immediately when no input is needed. Preserve uncertain, shared and review/reuse resources through their real owner; an open or running chat alone is not a retention reason.

Use `copy_run_inputs(project_root, source_root, destination_root, relative_paths)` for an explicit file whitelist; it verifies independent copied bytes/hashes and rejects overwrite, links and traversal. The resolver CLI can allocate and copy in one invocation:

```text
python workflow-skill/scripts/task_artifact_paths.py --project-root ROOT --task-id CHAT --create --copy-from PREVIOUS_ROOT --input fixtures/file.json --input images/input.png
```

Use the returned root and file hashes for readback. Omit copy options when no prior input is needed; never replace the whitelist with a directory clone.

Release disposable stage files, child activity and worktrees as soon as that unit's result is verified in its real owner under [Task Resource Lifecycle](task-resource-lifecycle.md). Do not wait for the whole chat or Ending to finish. Final deliverables and reusable environments leave scratch through verified delivery or owner handoff.

## Preserve real owners

- Maintained source/configuration, versioned non-runtime tests and requested final deliverables keep their declared owners. Required native runtime/build caches, canonical asset originals/history, project services and their real resource/recovery Cache owners are not ordinary AI scratch. Do not blanket move a project's Cache or reclassify task evidence as a runtime resource merely to retain it.
- Keep changing run inputs, parameters, execution state and one-off adapters in that execution's project Cache run directory; pass them as data to stable tools. Durable project knowledge stays only in the configured Obsidian vault. Skill folders and project `AGENTS.md` hold stable instructions, not run inventories or task logs.
- Image generation still follows the [image workflow](image-generation.md). Bind native downloads to the exact job and SHA, move unchanged accepted files into their actual asset/deliverable owner, then release task staging and transport duplicates after the required acceptance/sync readback. Set download paths inside the task run where the tool supports it; an unavoidable tool-owned staging copy is transferred and cleaned promptly, never adopted as permanent Downloads storage.
- One-off test/review recordings, native projects, build output, source clones and writable emulator disks stay in that execution's `temp-*` run while their actual consumer needs them, then close after verified consumption. Reuse or user review preserves the exact needed inputs through current consumer references; it does not turn a completed test into permanent `remote-*` storage. Versioned fixtures belong in the maintained test owner. Final assets, packages and genuinely reusable environments keep their verified final/resource owner. A prefix or adjacent metadata establishes neither durability nor remote synchronization.
- Before cleanup, verify final bytes and consuming references through a fresh reader. On pause/failure, preserve minimum recovery inputs/state in the declared recovery owner and remove independent disposable support. Keep active, shared, user-opened and useful review/reuse resources until their owners and references are verified; missing metadata never authorizes deletion.

## Migrate existing misplaced scratch

For an explicit request to clean one project's Cache, all Codex projects, or the whole computer, use [Cache cleanup](cache-cleanup.md). That request authorizes direct deletion of confirmed disposable legacy support within its selected scope after checking exact run identity and consumers. Preserve only resources with actual active, recovery, shared or review/reuse needs; activity elsewhere in the project or chat does not protect old runs. Migration is not a prerequisite for authorized deletion. Automatic checkpoints also cover exact disposable predecessors, registered completed/obsolete disposable runs immediately and foreign working runs inactive at least 24 hours; discovery of all filesystem roots is separate from this fast indexed pass.

Project Cache direct child directories must be `temp-*` or `remote-*`. New task scratch belongs in a fresh project Cache run. Flag other names, loose task outputs and legacy `tmp-*` as violations, inspect and fix their writing source, then delete obsolete contents. Transfer only concretely necessary inputs/results to their verified owner before removing a mixed directory; prefix changes alone never establish ownership or justify retaining garbage. Do not rewrite native nested cache layouts or classify source directories as disposable merely by name.

`remote-*` is a review candidate, not a retention exemption. Check its producer, native synchronization whitelist and actual long-term consumer; configuration, canonical assets and real service/runtime resources may remain with that verified owner. Scan/discovery inventories and allocation checkpoints expose these direct children as `remote_review` without traversing their payloads or granting deletion authority. Resolve the reported candidates within the authorized scope; an offline remote or missing owner evidence remains explicit. For consumed test payloads, fix the writer and stale consuming references, retire them through the existing identity/consumer guards, and read back local and remote absence separately. Preserve historical result identity where needed, while marking retired payloads unusable for future acceptance.

Select exact paths through creation history, file identity and current consumer checks. Preserve canonical resources, source, maintained tests, final deliverables, unrelated work and uncertain files. Stop only confirmed owned disposable activity before moving its backing files. Move authorized legacy scratch to its isolated project Cache owner, preserve bytes/hashes, update every affected consumer/reference and verify with a fresh reader before retiring the old location.

A migration is a separately authorized retention/move action, never a way to bypass a rejected deletion or other permission control. A rejected operation remains pending unless that control changes; report the exact target and reason. Do not infer migration authorization from a cleanup failure, broadly sweep project directories, or hide pending resources under a new name.

## Before staging and committing

Review the exact task path list, `git ls-files` and `git diff --cached --name-status`. Stage only maintained source/configuration and requested versioned deliverables. Temporary files never enter Git, regardless of filename or extension. Preserve unrelated index entries; use scoped paths rather than broad staging. Check for newly created project-local support/caches and remove only verified task-owned leftovers through their owner. Keep actual project runtime Cache ignored under its existing contract.

## Test file placement

- When project logic or goals change, inventory existing test files and their runner references. Remove obsolete and duplicate cases; revise a useful existing case before adding another file. Keep only tests that exercise a current behavior or a deliberate compatibility boundary.
- Put a nonshipping retained harness/fixture in its declared external resource owner. Tests required by source or a clean-clone release use the toolchain's versioned, non-runtime development area, such as a Skill's `tests/` or an appropriate Unity editor-only area; their run output and caches stay in the project Cache run. Keep tests out of runtime source and final deliverable folders.
- After moving or removing a test, update runner commands, imports, fixture paths, documentation, and release checks, then execute the affected test from its final location. Do not keep a stale copy at the old path.

## Portable paths and external resources

- This policy applies to every local-machine path in Skills, scripts, source, configuration, documentation and commands. Discover external/task roots at runtime; use project-relative paths only for actual project-owned source/resources. Never publish a user-specific home/drive absolute path or slash assumption.
- An AI-only external-path registry uses `{"schema_version": 2, "scope": "ai_only", "paths": {...}}`. Each entry records a `base` (`home` or `project`), a relative `path`, `kind` (`file|directory|application`), and a short `purpose`. Resolve the base at runtime. Never write an absolute path into code or configuration.
- Project source, runtime, tests, package scripts, build, CI, and shipped configuration must never read this registry. Memory Skills must never read or write it. Do not store credentials, tokens, secrets, business data, task transcripts, or memory locations in it; never commit, mirror, or publish it.
- Keep this private non-memory registry in a declared external AI resource owner, never project Cache or Codex storage. Validate an explicitly supplied external test fixture path first. Otherwise validate the registry schema, base, relative path, declared kind, existence and readability before use. If one entry is missing/stale, perform one bounded platform-aware discovery, update only that key, and replace atomically while preserving unrelated keys. Obsidian memory resolution remains with Project Memory.

## Project structure and cleanup

- Project-root `AGENTS.md` is a compact structural contract, not a project notebook. Keep only stable structure, ownership boundaries, critical entry points, hard constraints, project-wide conventions, a compact definition of done, and short pointers to owning documentation. Do not put implementation details, task history, logs, receipts, test results, generated data, long command blocks, or troubleshooting prose there.
- Maintain that contract and the project's `.agents/skills/ai-index` automatically through [Management's AI-index function](../../management-skill/references/project-ai-index.md) at start and finish. Prefer focused index documents over new nested `AGENTS.md` files; preserve existing scoped and tool-required guidance. For a real retained/shared Cache owner, record its stable boundary in the index and retain existing required local guidance. Keep changing run state with the resource owner. Ordinary task scratch needs no project guidance entry.
- Before acquiring or releasing a task-created path, runtime, application, or browser resource, apply [Task Resource Lifecycle](task-resource-lifecycle.md). Clean exact task-owned disposable resources after verified durable delivery or minimum recovery handoff. Bounds-check resolved targets and use one native platform shell or the portable helper; do not traverse symlinks/reparse points. Preserve unrelated, preexisting, shared, active, review/reuse and Unity-owned resources. Ending's [bounded resource audit](ending-resource-audit.md) checks confirmed leftovers from completed chats after applying their owners' cleanup first. Report concrete ownership/identity conflicts rather than claiming cleanup completed. Never use cleanup to control another Codex task, thread, session, or Ending, or purge Codex-managed storage.
- Final reports go only to the user-requested output location. Important retained resources are never deleted without explicit authorization. This policy restores project-Cache scratch placement; it does not relocate canonical runtime/assets or overwrite user `AGENTS.md` files during deployment.
