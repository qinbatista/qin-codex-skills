# Project Cache Artifact Policy

Read this reference before any task-selected file write, including browser evidence, helper/test output, and delegated work. Classify the file by its purpose before choosing its path. Maintained source/configuration and explicitly requested final deliverables keep their declared owners; a screenshot, JSON receipt, log, probe, or recovery observation does not become source merely because it is useful evidence.

## Before writing and committing

- Every temporary file must be under the resolved workspace's `Cache/temp-<name>/` or `Cache/tmp-<name>/` from its first write. Names such as `account-conversation-cleanup/`, `evidence/`, or `reports/` outside Cache do not create an exception. For projectless work, resolve the current task workspace and use its Cache. If that workspace is unavailable, report the path blocker before writing; never fall back to system Temp, Desktop, a source directory, or Codex session storage.
- Configure output paths, working directories, and child-process `TMPDIR`, `TMP`, and `TEMP` as applicable before running tools. Resolve and bounds-check task paths and reject links/reparse points that escape Cache. Tool-owned immutable outputs and recoverable installation transactions keep their explicit owners; ordinary task scratch cannot be reclassified as either.
- In a Git workspace, verify the exact proposed temporary path with `git check-ignore --no-index` and confirm `git ls-files -- <path>` is empty before writing. Add a narrow Cache ignore rule in its configuration owner if needed; an ignore rule does not untrack existing files. Never force-add temporary files.
- Before staging and again before committing, review the exact task path list and `git diff --cached --name-status`. Stage only maintained source/configuration and requested versioned deliverables. Exclude every temporary file regardless of filename or extension, including PNG screenshots and JSON cleanup receipts. Preserve unrelated index entries; a mixed index requires an isolated task commit, not a broad `git add -A`.
- For misplaced temporary files, verify exact identity and dependencies. Move only necessary pending recovery state into the declared Cache runtime/recovery owner, update its references, and read back its bytes; delete disposable evidence and empty directories after that handoff. Preserve originals, final assets, maintained tests, and unrelated work.

## Placement and retention

- Resolve the authoritative project root before the first project-support write. Put disposable evidence, receipts, logs, snapshots, generated media, comparisons, debug data, intermediate code, test results, and ordinary test scratch in that project's `Cache/temp-<name>/` or `Cache/tmp-<name>/`. Use a fresh task-owned directory or a context-managed temporary directory; delete it, including its empty root, at task completion after durable delivery is verified.
- Keep changing run inputs, parameter files, execution state, and one-off adapters in that same task directory. Pass them to stable local tools rather than rewriting a Skill or its scripts for each run. Maintained source/configuration and requested deliverables keep their declared owners; durable project knowledge stays in the central memory store, not Cache.
- Image downloads use the [image workflow](image-generation.md): immediately move unchanged native files to their bound owner/ID, register exact SHA and synchronization intent, then clear that job's staging and duplicates after verified acceptance and synchronization. Neither Downloads nor repeated temp copies become a resource owner.
- Use `Cache/remote-<name>/` only when the user or project contract explicitly requires retention under a real declared resource owner. Record its concrete project use, retention reason, owner, and sync status in that directory's metadata; link its stable ownership boundary from project guidance. The sync destination is pending until the owner selects it; never claim remote completion without separate sync and readback. Preserve verified retained resources during task cleanup. Preserve actual user review/reuse files and environments even if their metadata is missing; establish their owner and update references before removing backing scratch. Merely renaming `temp-*` or `tmp-*` to `remote-*` does not establish retention.
- Before cleanup, place final deliverables in their declared output or website/resource owner, update every durable reference, and verify bytes and the consumer through a fresh process or website readback as applicable. On pause or failure, move only minimum recovery inputs/state to the exact declared durable recovery owner and verify them; remove independent disposable scratch. Keep useful review images, documents, data, memories, test projects and reusable simulations; a known result does not make their backing files disposable. Release unused task browser/preview/terminal and process/network handles through their owning tools.
- Do not create new top-level `tmp/`, `tests/`, or `work/` support folders, and never use `~/.codex/cache` or `~/.codex/tmp` for project artifacts. If a legacy top-level directory already exists, preserve its contents and move it only through an authorized, ownership-safe migration.
- Keep `Cache/` ignored. A private AI-only registry for non-memory test fixture paths, when needed, belongs under `Cache/remote-ai-paths/registry.json`. Never put Obsidian vault pointers or memory data there.

## Test file placement

- When project logic or goals change, inventory existing test files and their runner references. Remove obsolete and duplicate cases; revise a useful existing case before adding another file. Keep only tests that exercise a current behavior or a deliberate compatibility boundary.
- Put a retained test harness under that project's `Cache/remote-<name>/` only if it still runs there and does not need to ship with source or a clean-clone release. Record its project use, reason, owner, and pending sync destination. Otherwise use the toolchain's versioned, non-runtime development area, such as a skill's `tests/` or an appropriate Unity editor-only area. Keep tests out of runtime source and deliverable folders.
- After moving or removing a test, update runner commands, imports, fixture paths, documentation, and release checks, then execute the affected test from its final location. Do not keep a stale copy at the old path.

## Portable paths and external resources

- This policy applies to every local-machine path written into a Skill, script, source file, configuration, documentation, or command, not only Cache paths. Use project-root-relative paths or discover the project root at runtime and join paths with native APIs. Never publish a user-specific POSIX home absolute path, Windows drive-letter absolute path, or slash assumption.
- An AI-only external-path registry uses `{"schema_version": 2, "scope": "ai_only", "paths": {...}}`. Each entry records a `base` (`home` or `project`), a relative `path`, `kind` (`file|directory|application`), and a short `purpose`. Resolve the base at runtime. Never write an absolute path into code or configuration.
- Project source, runtime, tests, package scripts, build, CI, and shipped configuration must never read this registry. Memory Skills must never read or write it. Do not store credentials, tokens, secrets, business data, task transcripts, or memory locations in it; never commit, mirror, or publish it.
- Validate an explicitly supplied external test fixture path first. Otherwise validate the registry schema, base, relative path, declared kind, existence, and readability before use. If one entry is missing or stale, perform one bounded platform-aware discovery, update only that key, and replace the registry atomically while preserving unrelated keys. Obsidian memory resolution uses an explicit vault, `CODEX_OBSIDIAN_VAULT`, an open memory vault in `obsidian.json`, or the dedicated default memory vault generated by Project Memory.

## Project structure and cleanup

- Project-root `AGENTS.md` is a compact structural contract, not a project notebook. Keep only stable structure, ownership boundaries, critical entry points, hard constraints, project-wide conventions, a compact definition of done, and short pointers to owning documentation. Do not put implementation details, task history, logs, receipts, test results, generated data, long command blocks, or troubleshooting prose there.
- Register each retained or shared Cache directory with one concise `AGENTS.md` registry entry describing its stable Cache-relative path, project use, retention reason, owner/source of truth, and a link to the owning source, project documentation, or a README. Keep changing run status, file inventories, and sync status in that directory's metadata; the sync destination remains pending until chosen. Update `AGENTS.md` only when structure, ownership, a critical entry point, or a hard constraint changes. Ordinary task scratch needs no registry entry and does not trigger Skill or `AGENTS.md` updates.
- Before acquiring or releasing a task-created path, runtime, application, or browser resource, apply [Task Resource Lifecycle](task-resource-lifecycle.md). Clean exact task-owned disposable resources after verified durable delivery or minimum recovery handoff. Bounds-check resolved targets and use one native platform shell or the portable helper; do not traverse symlinks/reparse points. Preserve unrelated, preexisting, shared, active, review/reuse and Unity-owned resources. Ending's [bounded resource audit](ending-resource-audit.md) checks confirmed leftovers from completed chats after applying their owners' cleanup first. Report concrete ownership/identity conflicts rather than claiming cleanup completed. Never use cleanup to control another Codex task, thread, session, or Ending, or purge Codex-managed storage.
- Final reports go only to the user-requested output location. Important retained Cache content is never deleted without explicit authorization.
