# Workflow Routing Matrix

Use this matrix from `workflow-skill` before any worker skill starts. First show the user-facing start diagram required by `SKILL.md`; then use the matching route row. Every row begins with `workflow-skill`; the remaining skills are executors selected by it. These rows are multi-select routes: combine them when the task spans several artifact types, but do not run unrelated rows as a checklist.

## Prompt Task Gate

Before selecting the `text`, `code`, `python`, or `mixed` row, check whether the request is actually about prompt behavior. Match the prompt route when the user mentions prompt wording, prompt files/templates/strings/constants, system/developer/user instructions, model or agent instructions, AI output behavior, extraction/generation/checker prompts, prompt tests, prompt review, or a prompt/rule that is not triggering.

Prompt route takes precedence over generic text work. If the prompt is embedded inside Python/C# executable behavior, combine the relevant code route with the prompt route instead of dropping the prompt workflow.

## Goal Check Rules

- Every route starts with `workflow-skill`; all later skills are executors.
- Every workflow-skill task starts with a user-facing start diagram: compact direct-route diagram for lightweight work, or task-specific Mermaid diagram plus target map for explicit work.
- For simple obvious low-risk actions, use `fast-path-simple`: execute directly with minimal local confirmation, then delegate the same task-local `Ending Workflow` task to subagent(s) without running `verify-skill`, reports, optimization, Obsidian recording, docs, Markdown updates, local mini tests, real tests, validation, verification, or extended real tests in the main path.
- For comprehensive or explicit workflows, stop the main lane at the `Main Goal Done Gate`: the requested edit, artifact, push, publish, command, or primary state change is complete and only required minimum precondition checks for public-safety, privacy, or irreversible-action safety ran in the main lane. Put local mini tests, local real testing, validation/verification, documentation, wiki/log/DailyLog/Obsidian, Markdown updates, sync/status checks, post-goal remote status/hash proof, and other post-goal updates into purpose-specific `Ending Workflow` subagent(s).
- Main-goal workers and Ending Workflow workers are separate lanes. A main-goal worker can be waited on only when its output is required to produce the requested result before `Main Goal Done Gate`. An Ending Workflow worker starts after that gate, runs in the background, and reports tests, validation, docs, memory, remote proof, visual review, or no-op inventory as follow-up.
- Ending Workflow Fan-Out uses multiple purpose-specific Ending Workflow subagents when a task has distinct closeout purposes such as verification/tests, local docs, Obsidian/wiki/DailyLog, remote sync/status proof, or visual/browser review.
- Parallel Ending Workflow Dispatch: when ending purposes are independent, spawn all independent Ending Workflow subagents in parallel before the final response. Start docs/wiki/memory, remote status proof, local document checks, visual/browser review, local mini tests, and real testing together unless one worker's output is a real dependency for another. The user does not wait for all background subagents to finish unless they explicitly asked to wait.
- Ending Workflow worker prompts must include the direct-execution contract: the worker is an Ending Workflow worker only, must not call `$workflow-skill`, must not restart global routing, must not create/spawn/resume/wait on subagents, and must do the assigned task directly with local tools, code, commands, and bounded file edits. If more delegation seems necessary, the worker reports blocked instead of spawning another worker.
- Ending Workflow Related Update Scope is proportional and document-related: check relevant log/history and directly related docs/wiki/Obsidian/Markdown pages for the current task, update stale or missing related information, and stop when those related updates are done. Do not set fixed time limits in the skill. Do not bundle previous tasks, scan the whole repo, or scan the whole vault unless the current result depends on it.
- Ending no-op requires a `Related Closeout Inventory`: the worker must inspect related docs/wiki/Obsidian/Markdown/log sources for touched files, user corrections, global skill changes, project contract/schema/mock API/fixture/public output shape/API documentation behavior changes, then either update stale related information or report checked sources with per-source reasons.
- Final response is blocked only until the `Ending Workflow Tool-Call Gate` has dispatch evidence: worker id/name, purpose, running status, or `Ending Workflow blocked: no subagent tool`. A plan, queue note, intention, or written promise is not delegation.
- For Python/C# executable behavior, the order must be `code-skill -> verify-skill`.
- Run the Prompt Task Gate before generic text/code routing. For any standalone prompt-related task, use the prompt route; start by showing `Prompt idea -> Prompt goal -> Problems -> Solution`; add `code-skill` only when the prompt is being embedded in Python or C# executable code.
- For global skill work, run `management-skill` before edits and for the actual push when the user asks to publish; after the edit or push succeeds, put broad validation, post-push status/hash proof, docs, and Obsidian/wiki/log closeout into Ending Workflow subagent(s).
- Passing evidence must include real `Input`, `Used`, `Output`, and `Why Pass` when a report is generated.
- If the observed output does not satisfy the goal target, continue the loop instead of finishing.
- After a user-facing task passes, run `optimization-skill` only when the user explicitly asks, the same workflow has repeated at least three times, or the workflow is clearly stable and likely reusable. Verify optimized behavior again through `verify-skill`.
