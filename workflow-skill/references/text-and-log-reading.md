# Bounded text and log reading

Read to answer a specific question. Large machine logs, generated text and command output must not be dumped into the conversation or loaded wholesale merely to discover what matters. Output truncation is a failed reading strategy: narrow the query instead of increasing the output limit or requesting everything again.

## Diagnose machine logs from the end

1. Identify the exact file/job, current attempt and time range. Inspect metadata without printing content. For chronological build, test, compiler, runtime and service logs, read the last bounded page first, typically 80–200 lines with a byte/character cap. Use the provider's latest-page/cursor API or a tail-capable local reader. If a provider returns newest-first records, use its newest page directly.
2. Read each page in its original chronological order so stack traces remain understandable. If the final page lacks the failure, move to the preceding page with a stable cursor or explicit range; do not repeatedly expand the tail until the whole log is returned. Check for append, truncation or rotation before reusing offsets and stay within the same attempt.
3. Extract concrete search terms from what you observed: exception/error code, failing test, file or symbol, request/job ID, timestamp, or `Caused by`. Search those terms in the relevant file/time window, returning bounded matches with line numbers or timestamps. Start with recent matches; `rg -m` alone selects the first matches and is not a latest-match query. Narrow noisy results by attempt, component or exact literal before widening scope.
4. Read a small window around relevant matches, expanding just enough to include the complete exception chain and meaningful preceding events. A final nonzero-exit or build-failed summary is a symptom; trace it backward to the earliest causative error in that attempt. Older failures, expected negative tests and unrelated concurrent jobs are not evidence for this failure. Empty keyword results do not prove success: inspect the preceding page and adapt terms to the log format.
5. Stop once the cause and required evidence are established. Report the source, attempt/time or line range, concise relevant excerpt and any unresolved gap. Never paste the complete successful log or an entire search result list.

## Bound the reader, not just the display

- Use tools that select before returning content. Do not use `cat`, unrestricted `Get-Content`, `read_text()`/`readlines()` followed by slicing, or an unbounded tool response to inspect an oversized log. Stream searches and seek/tail reads may examine bytes internally without placing the whole file in memory or the model context.
- On macOS/Linux, start with `tail -n 120 -- "$log"`; read the preceding page with `tail -n 240 -- "$log" | head -n 120`. For ordinary line-sized logs, `rg -n -i -- 'exception|fatal|caused by|error' "$log" | tail -n 40` returns recent candidate locations; replace broad terms with observed identifiers, then read the selected context range. On Windows use `Get-Content -LiteralPath $log -Tail 120`, with bounded paging or the provider's cursor for earlier records. Keep paths quoted and use literal search (`rg -F`) for IDs containing regex characters.
- Line limits alone do not bound huge single-line JSON/minified records. Check size first, use a byte-capped tail/seek reader (for example `tail -c 16384` on macOS/Linux), and select structured fields or bounded string slices before returning output. Mark partial records/excerpts explicitly; retain full exception context only when needed to resolve the cause.
- For commands expected to emit large output, capture stdout/stderr in the current external task run from launch and retain the actual command exit code separately. Then inspect the tail and keyword/context windows. A successful `tail` or search pipeline does not establish command success. For large JSON reports, parse and return status, counts and selected failing entries rather than serializing the whole object.

## Other long text

For source code, documentation and structured reports, first use the project index, headings, symbols, keys or a targeted search; read only relevant sections and necessary relationships. Do not mechanically reverse a source file or ordinary document. Small, cohesive files or an explicitly requested full-document review can justify complete reading; explain why completeness is needed and still page oversized material. Preserve enough context to understand the actual contract without reading unrelated sections.
