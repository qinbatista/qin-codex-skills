# Resource ownership

Apply the [unit cleanup plan](project-cache-artifact-policy.md#plan-before-producing-files) before implementation and the [project Cache artifact policy](project-cache-artifact-policy.md) before acquisition: each request or test/build/package/deploy unit gets a fresh project Cache run, even within one chat/task. Track exact temporary files, runtimes and UI surfaces when cleanup needs coordination. Use optional `scripts/task_resource_ledger.py` only for actual dependent consumers or required native handoff; never create a shared scratch pool or extra ledger to save future work. New ledgers bind the exact task and `run_id`. Legacy deterministic roots support readback and original-owner cleanup, never new write reuse; project Cache ledgers remain bound to their exact task and lifecycle owner.

Image jobs follow [image generation and closure](image-generation.md). Downloads move immediately to the bound owner; verified acceptance and synchronization release disposable transport copies. Confirmed account-action submission and bounded final tab cleanup do not gate independent work. Keep backend deletion, tab closure and scratch absence as separate verified or pending states; preserve exact recovery targets without endless readback loops.

## Clean up each step

Cleanup is part of preparation, research, implementation and testing, including retries and interrupted attempts. Keep each new resource's exact handle or path from its creation receipt. A tab already open when the task starts stays with its original owner. Apply the same rule to windows and processes. A matching title, URL, application name or directory name alone cannot establish ownership.

- **CPU and GPU work.** Stop scheduling work when the result is ready. Finish or cancel outstanding jobs through their native owner, then wait for their terminal state. Join owned workers and child processes, including children that outlive the launcher. For a remote job, check the scheduler or provider using its job ID. Preserve a job the user asked to keep running.
- **RAM and GPU memory.** After outstanding work finishes, release the task's buffers, mapped files, model instances and device allocations through the runtime that owns them. In a shared runtime, release the task's references or lease and preserve other consumers. For an isolated worker, verified process exit releases its private address space. Check the runtime's allocation counter or handle when available. Report reclaimed bytes only when measured at that scope. System memory totals can include reusable OS or driver caches.
- **Research tabs.** After capturing the needed result, close each task-created tab through the browser and check that its ID is absent from a fresh tab list. Keep a requested live result or a tab needed for user input through the browser's deliverable or handoff mechanism. If the browser releases tabs automatically at a turn boundary, distinguish scheduled closure from observed absence.
- **Previews and applications.** After verifying the preview, close its owned tab or window. Gracefully stop the exact server, worker or application instance the task launched once its last consumer is done. Verify exit through its owner. In a shared application, close only the task-created surface. Preserve unsaved work.
- **Temporary test folders.** Put fixtures, logs and failed attempts in the step's registered Cache run. Move requested outputs to their final owner, update references and verify the delivered bytes from a fresh process or website request. After closing anything using the folder, run the delivery checkpoint and verify both the directory and its registration are gone.

For example, a local preview may use two research tabs, a preview tab, a server and a test folder. Close each research tab after taking its result. Once the preview check finishes, close the preview tab, stop and wait for the server, then release the folder. If the user asks to keep the preview running, preserve its server and necessary files too. If one close fails, report the exact handle and reason, preserve its dependencies and release the independent resources.

Close owned sockets, file handles and terminal sessions, unsubscribe listeners and cancel timers or transfers once their consumer finishes. Verify release through the service or runtime and remove completed ledgers, markers and empty run directories. Report the verified result and run `checkpoint --phase delivery` for registered scratch before the next unit or final response.

For a retry of a registered Cache run, use the policy's [continuation command](project-cache-artifact-policy.md#separate-executions-and-continuation). Check the returned status and use the new root only after the transfer and predecessor cleanup complete. For a separate ledger-backed destination, reserve each absent input path or its containing directory tree with `acquire_path` before copying, track created parent directories, and call `seal_path` after byte readback. Verify consumer references before retiring their old dependencies. Preserve exact necessary active/recovery inputs, explicit user holds and source/native owners. Handle an uncertain consumer at its exact run boundary.

On pause or failure, transfer only the minimum inputs and resumable state required for recovery to the exact declared recovery owner, verify them, and remove independent disposable scratch. Do a bounded classification of missing metadata now; generic review/reuse and possible future setup are not retention reasons. Completed disposable evidence never authorizes indefinite temp retention. Consumers that need the result must be rebound to the verified durable owner; renaming a temp directory to `remote-*` is not a handoff. A verified `Cache/remote-*` is retained under its actual resource owner, not merely its prefix.

Release disposable resources in reverse acquisition order. Resolve and bounds-check every deletion target against the exact task root; use one native platform shell end to end or the portable helper, never shell-built path lists. Preserve unrelated, pre-existing, shared, and application-owned resources. Do not traverse symlinks or reparse points. Report ownership or identity conflicts for the affected cleanup. The ledger's `durable-handoff` verifies a real owner record and bytes before releasing scratch dependencies; `finalize` removes an exact empty task root only after all recorded resources are closed and no unknown files remain.

## Task-transition cleanup checkpoint

Run this checkpoint both when a unit finishes and when the next request/unit starts. A change of subject, project, code target, packaging job or testing goal triggers it even when the chat stays open. The new task need not depend on the old one; no dependency means there is no continuation-input reason to retain the old scratch.

1. Run the [local executable checkpoint](cache-cleanup.md#local-index-and-executable-checkpoints) and inspect the preceding unit's exact resources. Include known completed/obsolete predecessors outside the new project immediately, including registered completed/obsolete disposable runs from other tasks; foreign working runs require no heartbeat or recursive changes for at least 48 hours. Process the explicit owners first and read back their closure separately from unrelated pending records. Resume interrupted deletion only with its unchanged original proof and fresh guards. When needed, use bounded originating/recent-chat readbacks to recover exact owners. Inspect naming violations and their producers; do not recursively sweep the whole computer on every checkpoint. Missing ownership blocks that candidate only while its purpose is checked.
2. Check actual consumers and final-output delivery. Retain an item only for a concrete current need: necessary active input, minimum input for an identified recovery action, or an explicit user hold. Requested final files must leave scratch through verified handoff. Name the exact files, actual consumer, necessity and ending condition in the cleanup plan. Remove all other files before setting retained/recovery. Resolve missing/expired retention reasons at the next checkpoint instead of treating `retained` or `recovery` labels as permanent exemptions. “Maybe useful later,” “the chat/project is still open,” “it was a build,” and “Ending will handle it” are not retention reasons. Missing metadata alone proves neither usefulness nor disposability; make a bounded check of the original purpose and consumers rather than inventing a future need.
3. For unrelated work, delete the completed predecessor's confirmed disposable support directly; allocate the next run without copying old scratch. For related work, transfer only the exact useful inputs and verify their bytes/references, then delete the rest. This applies equally to code probes, test output, logs, screenshots, duplicate downloads, package/build staging, disposable clones/worktrees and obsolete intermediate archives. Preserve maintained source, canonical assets/runtime caches, requested final packages and real recovery/review resources.
4. Release idle owned processes/surfaces through their owner, then remove exact disposable files and empty run roots using the existing bounded helpers/native owners. Standing authorization includes confirmed Skill-generated legacy `Cache/temp-*` from these predecessors; use [Cache cleanup's exact-run checks](cache-cleanup.md#check-exact-runs-and-consumers) without requiring another cleanup request or migrating garbage first. Never bypass a rejected operation, delete through symlinks, or purge Codex-managed storage.
5. Read back absence and retained consumer references. Briefly report actual removals and measured disk bytes when available, plus exact retained/blocked items and reasons. A list of candidates or promise to clean later is not completion. Do not postpone all reclamation because one item is uncertain; finish eligible siblings before proceeding with new disk-heavy work. If none exist, record an explicit no-leftovers result without creating a report file.

This checkpoint is performed by the active task. Ending is a residual audit, never a prerequisite or a substitute. Do not create an automation or wait for an old chat to close. Retention decisions expire when their concrete consumer finishes; check them again at the next transition.

Commit, merge, delivery and verification are immediate cleanup checkpoints too. After source changes are safely committed or integrated into their required owner, remove unused patch copies, merge probes, duplicate source snapshots and integration staging. After a check has an established result, remove its unused fixtures, scratch projects, logs and build/package intermediates once any required evidence or recovery inputs have been handed off. Failed checks do not justify retaining the entire workspace: keep only concrete minimum recovery inputs. Generic review/reuse, shared file pools and saving setup do not justify retention. Do not retain disposable material merely as extra insurance for code already preserved in Git or results already recorded. A commit or passing check alone does not authorize deleting the authoritative checkout, undelivered commits, required final packages or another consumer's files; disposable checkouts still follow the native-owner rules below. Apply these checkpoints immediately, not only at the next user request.

## Worktrees and disposable checkouts

Release a unit's disposable build/test checkout when verified output no longer needs it. For a source worktree, first commit task-owned changes, integrate/deliver them to the authorized branch and verify any required remote hash. Inspect the exact worktree, branch, dirty/index state and current consumers immediately before removal. Preserve unrelated edits, uncommitted work and explicitly retained checkouts; move required outputs or minimum recovery files to their verified owner first.

Use `git worktree remove` for a clean ordinary worktree, or Codex's `archive_worktree` for its exact attached managed owner; the latter retains a recoverable snapshot while removing the checkout. Use the owner's native removal for a disposable clone. Never force-remove a dirty worktree or delete its directory behind Git/Codex. Read back checkout absence and registration, then close the delivered task branch under [Git branch ownership](../SKILL.md#git-branch-ownership). This applies to every task branch name and includes its published head and stale tracking refs. An active chat does not justify keeping an unused earlier worktree; an active consumer of that checkout does.

Cleanup never controls, interrupts, archives, or deletes any Codex task/session, user-opened tab, or Codex-managed session record. Complete scoped memory and the bounded resource audit inline. Do not create automatic Ending chats or delete their session records. Recheck exact run/resource liveness and purpose before release; protect active/shared resources and the user's Codex experience. Follow the owning Skill first, then finish safe missed cleanup or report precise pending items.
