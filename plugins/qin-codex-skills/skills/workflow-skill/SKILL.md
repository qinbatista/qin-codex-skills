# Workflow

Before implementation or any payload write, make the [unit cleanup plan](references/project-cache-artifact-policy.md#plan-before-producing-files): purpose, deletion set, final destinations, and exact necessary retained files with consumers and end conditions. Default to deleting all scratch; do not create shared pools, convenience backups or speculative reuse copies. Apply the [project Cache artifact policy](references/project-cache-artifact-policy.md). Allocate a fresh `Cache/temp-<task-key>-<run-id>/` with the actual producer from the first write for each request or test/build/package/deploy work unit. A requested generator's required producer Cache is authorized without another question; receiving-project tests and output keep their own Cache. Share exact run ownership with dependent tools and delegates. Maintained source, final deliverables and real runtime/assets keep their owners; inspect exact paths and the Git index before committing.

Default new Cache output to `Cache/temp-*` whenever ownership, the consumer, or the need for synchronization is unclear. Reserve `Cache/remote-*` for exact files a Git-tracked project contract declares for a lasting consumer, with a verified synchronization route. Follow the [artifact policy](references/project-cache-artifact-policy.md) for allowlisting and readback. Write every run's intermediates and test output directly to its own `temp-*`, including output from a producer in `remote-*`.

Before the first payload write, record the workspace baseline and each producer's assigned run. Track exact paths and handles as tools create them for the [task leftover check](references/ending-resource-audit.md#check-and-reclaim-task-leftovers).

Apply [Task Analyze](../task-analyze-skill/SKILL.md) for correct names and the opening brief. Follow its [action completion rule](../task-analyze-skill/SKILL.md#complete-action-requests) from defining the final result and acceptance criteria through verification and delivery.

Follow [Task Analyze's final Skill report](../task-analyze-skill/SKILL.md#mandatory-visible-skill-reporting): keep an internal record of exact Skills actually used, their steps or actions and reasons. Gather delegated branch use for one parent-visible final summary; ordinary progress updates need no repeated Skill list.

For every UI or visual presentation task, including websites, PDF reports, documents, and slide presentations, read the [shared readable UI rules](references/readable-ui.md). Apply them even without code changes and when another Skill owns rendering or export.

For image generation, edits, retries, or batches, follow [image generation and closure](references/image-generation.md): use the required browser entry, prepare downstream work while generation runs, move native downloads into their exact owner, and finish bounded cleanup without blocking independent jobs.

## Long text and machine logs

Use [bounded text and log reading](references/text-and-log-reading.md) for long text, build/test output and machine error logs. Start chronological logs at the last page, move backward only as needed, then search specific keywords and read bounded context. Never dump the entire file or start with its first page by default.

## Browser testing

For any browser-based test, prefer the Codex or ChatGPT built-in browser surface. Use a named external browser only when the user explicitly requests that browser. If the built-in browser is unavailable, record that limitation and do not silently switch browsers or present a fallback as equivalent evidence. Keep task-created browser surfaces hidden unless the user asks to show them; retain user-opened and shared surfaces.

## Keep work moving

Start every ready independent branch promptly through concurrent tools or subagents with clear goals and disjoint write ownership. Serialize only genuine prerequisites, shared mutable owners and required authorization. Join a branch when its output is needed. For example, generate an image while a separate branch cleans confirmed disposable files; prepare output paths, layout inputs and QA criteria before the image arrives. Never delete an active job's inputs or backing resources.

Prefer events or completion notifications to polling. Use bounded checks with backoff while doing other ready work. If a check budget expires or a client stays stale, record the exact job, latest authoritative state and next recovery action. Continue through the service's status interface, a supported wait, or another viable recovery path. Apply Task Analyze's blocker rule once no useful authorized action remains. Check the existing submission before retrying to prevent duplicates.

Close resources and memory inline. Codex chats/sessions are user-managed; do not create, archive or delete Ending conversations automatically.

An authoritative receipt proves submission. When submission is the requested endpoint, use at most one immediate and one bounded final readback. When the requested endpoint is backend completion, follow the job to its authoritative final state and verify its output. Return to exact owned tabs during final cleanup and close those no longer needed. Actual output acceptance, byte verification and irreversible-action authorization still govern their real dependents.

## Monitor Mode

Use [Monitor Mode](references/monitor-mode.md) when the user asks to monitor another chat, or a long task needs continuing supervision and repeated verification to establish its final result. Keep the current chat as monitor and create authorized worker chats for independently owned modules in the same project. Work on the same module, function or shared mutable owner stays in this chat with subagents and coordinated writes. Duration alone does not justify a separate chat.

Check every five minutes, with earlier attention for completion or actionable failures. Compare progress with the user's scope, owning Skills, exact-project memory and current evidence. Stay quiet while work is on course; send brief steering only for a concrete deviation or blocker. Stop confirmed out-of-scope work through a supported control, or request a pause and verify acknowledgement when only messaging is available. Verify the agreed final result before closing supervision.

## Cleanup at every task transition

At inline closeout, run the [task leftover check](references/ending-resource-audit.md#check-and-reclaim-task-leftovers) for resources created by this task wherever its tools placed them.

Manage Cache by the requested end goal. After a verified upload, submission, test or delivery consumes an item, immediately remove unused local packages, exports, compiled intermediates and isolated source projects through their native owner. A package is a final deliverable only when the user needs a local package. Keep only exact necessary active/recovery inputs or explicit user holds from the plan. Put requested final files in their real owner outside scratch. After the verified result is reported, run `checkpoint --phase delivery` immediately and read back absence, even within the same chat. Generic review/reuse, saving setup and backup insurance never justify retention; 48 hours is only an abandoned-run fallback. Never delete Codex chats, sessions or databases; the user manages those manually. Do not create an automatic Ending chat.

At current-project startup and finish, read its AI-index `cache/README.md` and `cache/owners.json`, run cleanup, then refresh bounded current state with Management’s `project_ai_index.py cache --project-root ROOT --apply`. The ignored `cache/current.json` replaces the previous snapshot; removed payloads disappear instead of accumulating history. Reference lookups remain read-only.

At the start of every new user request or distinct work unit, including unrelated work in the same chat, apply the [task-transition cleanup checkpoint](references/task-resource-lifecycle.md#task-transition-cleanup-checkpoint) before producing new scratch or starting another build/package/test. Reclaim completed predecessors' confirmed unused support immediately; do not wait for chat closure, Ending, a separate cleanup request, a disk-space threshold or a time-to-live. This is standing authorization, not an optional suggestion. Cleanup failure blocks only the affected resource, not independent new work.

When a retry replaces a known run of the same task, use the [allocator's continuation command](references/project-cache-artifact-policy.md#separate-executions-and-continuation). It prepares a fresh directory, transfers only the named inputs and confirms removal of the previous run before returning the environment for the retry. Select the exact previous run so other units can keep their own directories.

Use the local [Cache cleanup helper](references/cache-cleanup.md#local-index-and-executable-checkpoints) at start, transition and finish. Process explicit owners first, then completed or obsolete disposable runs and resumable deletions. Check the remaining runs oldest heartbeat first. Abandoned runs require 48 hours without heartbeat or descendant changes and fresh consumer checks. Resume interrupted deletion from its unchanged original proof. Review missing retention evidence and repair producers of obsolete Cache entries.

Keep exact recorded user holds through automatic expiry. Release them through their owner after the user ends the hold.

The helper unlinks an owned run's internal symlinks and closed FIFO/socket nodes without following them after fresh consumer checks. Escaping links, reparse points, mounts, hard links and device nodes remain protected. Complete runs containing ordinary isolated tool installations must not remain indefinitely just because those installations contain internal links.

## Requested Cache cleanup

When the user asks to clean Cache, `temp-*`, all Codex projects, or the whole computer, follow [Cache cleanup](references/cache-cleanup.md). Match the requested scope, enumerate exact runs and consumers, then delete only confirmed disposable Skill-generated support. A running project or chat protects only resources it still uses; completed earlier runs may be cleaned immediately. An explicit cleanup request covers eligible legacy `Cache/temp-*` directly; no migration or routine confirmation is required.

When the user requests daily cleanup, configure one local schedule and use the [multi-project sweep](references/cache-cleanup.md#daily-multi-project-sweep). Run the first sweep immediately if requested. Continue independent tasks after the current project's checkpoint and report exact pending owners separately.

## Git branch ownership

- At the start or resume of every task that changes a Git project, read its branch and merge requirements before switching or editing. Follow an explicit task branch choice or a project-specific Git workflow, including its worktree, integration and publication rules. Apply the defaults below when neither supplies a different workflow. For read-only work, inspect the checkout without switching it.
- Select the project's actual `master` or `main` as the base and delivery branch, regardless of the current branch or a detached HEAD. Use repository guidance, existing upstream configuration and the configured remote's symbolic `HEAD` to resolve the primary branch when both names exist. Confirm the exact upstream before fetching or pushing. Switch safely to the primary branch before edits, or use its existing checkout if it is held elsewhere. If that checkout requires isolation, start a worktree from the updated primary base. Announce the selected branch and upstream and proceed under standing authorization.
- Preserve unfinished files, staged changes, existing branches, unique commits and active checkouts. Include only reviewed, completed changes and commits within the task's scope. A missing or ambiguous primary branch or tracking target requires concrete resolution before using it. If the primary branch is known but its upstream is unavailable, commit verified work wherever safe and report the exact pending integration or delivery with its commit SHA. Preserve any explicit hold, local-only or no-push instruction.

## Worktree isolation

- Before editing, compare the planned files, shared generated outputs and dependencies against dirty or staged paths and active task ownership. Inspect `git status`, `git diff --cached`, `git worktree list` and any in-progress Git operation. Work directly on the primary checkout when safe. If concurrent work overlaps, switching would disturb existing work, or the task genuinely needs an independent checkout, create one local `codex/<task>` branch and worktree from the freshly verified primary base. An attached writable branch preserves task commits. Keep simultaneous ref and index writes serialized.
- Check the cost of materializing tracked files, including large files, LFS and submodules, and the cost of recompiling or reimporting a project. A linked worktree shares Git objects but needs its own working files. Use a sparse checkout if the task's dependency closure permits it. Materialize only needed inputs, leave the original build/import cache with its native consumer, and avoid copying untracked files, ignored caches, dependencies, build outputs or entire projects. Use the exact Git or Codex resource owner and the project's Cache policy for task support. [Worktree lifecycle](references/task-resource-lifecycle.md#worktrees-and-disposable-checkouts)
- Finish and verify the task in its worktree. Refresh the primary upstream, then rebase the unpublished task commits onto the updated primary tip when needed. If revising a prior decision, amend or squash only task-owned unpublished commits and verify the resulting tree. Use a new corrective commit or revert for changes already published. Fast-forward the primary branch to the verified task tip in its own checkout as soon as the work is ready. Resolve genuine overlap without losing either side and recheck affected behavior. Publish the primary branch through its configured upstream. Remove the clean task worktree and delete its local branch after primary delivery and fresh readback prove the commits are integrated. If an active writer or unresolved conflict prevents landing, preserve the exact committed recovery state and continue once that dependency is resolved.

## Linear local updates

Keep every ordinary update on one linear history. Fetch the actual configured upstream; fast-forward upstream-only updates with `git merge --no-autostash --ff-only <fetched-tip>`. For divergence, compare both sides and replay only verified unpublished local commits with `git -c rebase.updateRefs=false rebase --no-autostash --no-rebase-merges <fetched-tip>`. Automatic pull workers use that same policy for compatible clean divergence when publication identity is established; conflicts, dirty/index work, active operations, local merge-only changes or unknown publication state remain recoverable pending work. Never create a merge commit or use `--rebase-merges`, `--no-ff`, or `pull --no-rebase`, and never make a worker's policy depend on test-output variables. A local pull does not authorize an automatic commit or remote push.

Configure each managed checkout with `pull.rebase=true`, `branch.<current>.rebase=true`, `pull.ff=true`, `merge.ff=only`, `rebase.rebaseMerges=false` and `rebase.updateRefs=false`. This makes ordinary `git pull` replay local commits and allows upstream-only fast-forwards; replace an inherited `pull.ff=only` override that would block divergence replay. Explicit automation passes `--no-autostash` and preserves staged, unstaged, untracked, active peer and recovery work. Verify the effective values at the actual checkout rather than assuming an installed Skill changed Git configuration.

An explicit request to flatten existing published merge history authorizes that narrowly scoped history repair; do not treat the ordinary no-rewrite rule as a reason to deliver only an isolated candidate or request the same authorization again. Preserve substantive side commits, merge-only changes, concurrent commits, final file bytes, and the original tip through native Git recovery. Publish only the selected branch with an exact-old-tip transaction or a specifically authorized lease-protected replacement, preserving ordinary receiver protections. Finish by reading back local, tracking and fresh remote tips, checking the complete reachable merge count and preserving unrelated dirty work.

When pulling an upstream that was explicitly flattened, use the native repair's exact old/new mapping or independently verified equivalent commit trees to locate the replacement base. Replay only genuinely newer local commits with `rebase --no-autostash --no-rebase-merges --onto <replacement-base> <old-base>`; do not replay superseded published ancestry or recreate its merge graph. Prove the old base, replacement and substantive content before moving local refs, retain exact recovery inputs, and verify the resulting files and configured upstream. An unverified rewrite or uncertain content remains pending; never use a blanket reset, discard local work or force-push as ordinary pull recovery.

## Execute

Every task that changes a Git-managed project automatically includes integration, verification and a commit, from a one-line fix to a large change. Normally push the delivery branch through its configured upstream and read back the remote ref in the same task. This standing authorization requires no routine commit, integration or push confirmation. Apply the selected project's workflow and honor explicit read-only, hold, local-only or no-push instructions.

Fetch and integrate the latest configured delivery upstream before starting edits, before each commit and again before each push. For isolated work, refresh that same primary upstream and integrate the latest primary base into the task branch before committing. If integration requires a clean tree, set aside only exact task-owned changes and restore them with their index state. After affected checks pass, stage only completed in-scope work and commit promptly. Review both intents when upstream changed and rerun affected checks after integration. Use normal pushes to the verified delivery ref. Temporary task branches stay local. Apply the linear update policy to manual pulls, background source checks, Skill updates and ordinary delivery under the same project precedence. [Linear local updates](#linear-local-updates)

Recover rejected pushes, transient transport failures and failed remote readbacks in the same task. Re-establish access, freshly inspect the remote to distinguish an accepted push from a failed submission, integrate any new upstream work and retry the necessary steps while a useful authorized route remains. One timeout, a failed command, a fixed retry count or a successful local commit never establishes completion or a permanent blocker. Stop affected delivery only for an evidenced condition that requires unavailable access, input or authorization; report it as pending with exact commits and recovery state, never as completed work.

Declare Git delivery complete after a fresh remote-ref readback matches local delivery HEAD, all task changes are committed on that branch and the task's temporary checkout and branch are closed. For authorized local-only work, verify the same local result. Report the branch, upstream and delivered commit hash. For a genuine blocker, report the exact unpushed SHA, recovery state and the dependency needed to proceed. Restore and verify every temporary integration stash in the same task, then drop only that exact consumed stash. Preserve unrelated stashes, branches and live checkouts.

1. Identify the result, project and constraints. Apply [automatic project AI index](../management-skill/references/project-ai-index.md) at start/resume: apply it only to the current task project: check presence, ask before first bootstrap, and otherwise reuse focused routes. Reading, searching or consulting another project does not switch the current project and needs no AI-index prompt or maintenance there. Do not discover an unindexed project before that consent. Read exact project/module/file/symbol memory through [Project Memory](../project-memory-skill/SKILL.md); skip absent entries and keep cross-project references explicit.
2. Preview the branches, qualitative difficulty, known models and real dependencies through Task Analyze, then proceed without a routine approval pause.
3. Apply the ready-work policy above. Start independent branches together, prepare downstream work during external waits, and integrate outputs only at their actual join points.
4. Reconcile root `AGENTS.md` and the project index with established user intent and affected source structure before final verification and authorized Git delivery. Verify changed code or consequential results using [Verify](../verify-skill/SKILL.md); use the smallest real boundary without starting the whole project unless requested. Complete the scoped residual guidance check in this chat.
5. At each work unit's verified delivery, release its exact disposable scratch, test/build intermediates, idle surfaces and owned worktrees through [resource ownership](references/task-resource-lifecycle.md). A long-running chat or later work unit does not delay this cleanup. Use the continuation command for an exact predecessor. Retain only exact necessary inputs or explicit user holds with an actual owner and ending condition. Release independent disposable material. Report result, cleanup and concrete ownership/API blockers, distinguishing source edits, installation and publication.
6. Finish scoped memory/resource closure inline under Project Memory. Never create an automatic Ending chat or delete Codex session records; the user manages them manually.

## Boundaries

Preserve unrelated work. Perform reversible actions within the request; obtain authorization for actions outside it. Never message others without explicit authorization. Report only results supported by evidence.

Apply [portable, quiet execution](../code-skill/references/skill-platform-compatibility.md) to all scripts, tests, and background work, including delegated and nested launches. Capture output without visible windows or focus changes; opening a terminal, browser, report, or app requires an explicit request to show it.

Use [resource ownership](references/task-resource-lifecycle.md) and the [project Cache artifact policy](references/project-cache-artifact-policy.md) when creating temporary resources. Ordinary work needs no extra ledger; record exact handles/paths when cleanup spans tasks or consumers. Never sweep Codex-managed storage or affect active/shared/user-opened resources.

The user gives standing authorization to delete task-owned disposable local Cache/scratch, verified download duplicates, and cloud files generated by the task, including Google and ChatGPT files. After exact ownership, consumer checks and required output handoff, perform eligible cleanup directly without another permission question; follow the provider's normal recovery flow and read back the result. This does not authorize deleting formal originals, requested results, active/shared resources or unrelated user files. If a higher-priority tool rule requires action-time confirmation for an irreversible deletion, request only that required confirmation for the concrete batch; an already confirmed unchanged batch needs no repeat question. Preserve and report blocked targets without bypassing the control.

Ordinary task results update their source, outputs or project memory. Automatically maintain project root guidance and AI-index routes under [their global owner](../management-skill/references/project-ai-index.md); other Skill edits still follow the [authoring rules](../management-skill/SKILL.md#authoring-rules).
